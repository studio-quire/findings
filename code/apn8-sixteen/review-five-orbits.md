# Review of five's orbit reduction (--reps), 2026-11-06

Fresh Claude Opus 5.5, asked by Rowen to try to break it. Scope: cfc3795 and 10d6aaf (`--reps`, `is_rep`, `--p1all`, five_aut.py,
five_orbits.cpp, five_cores.cmd, five_slices.py). Scripts and outputs: runs/i12/review/ (not in git).

## Verdict

**The reduction is valid and the implementation does what the valid statement needs. I found nothing that could change the answer,
and search A does not need to be stopped or restarted.** Below that: two driver gaps that delay an alarm rather than lose it, one
overclaim in a comment, and stale documentation that matters for the page. They're ranked in "Findings".

## The statement that has to be true

Write S8 o g for {B(g x, g y) : B in S8}. For a set P of five pairwise disjoint solids, let an S8 over P be an APN space whose rank-4
radicals are exactly P, and core(S8) the span of its five rank-4 forms. Let Cores(P) be the spans of one form per solid, each with
that solid as radical, in which every nonzero element is bent, rank 6 with its radical inside the holes, or rank 4 with a solid as
radical (each solid once), all radicals pairwise disjoint.

1. rad(B o g) = g^-1 rad(B). So for g in Aut(P) = Stab_GL(8,2)(P as a set), S8 o g is an APN space over P with the same rank
   distribution, and holes go to holes. g may permute the solids; nothing below uses their order.
2. core(S8 o g) = core(S8) o g, and core(S8) is in Cores(P), because each sub-span of an S8 passes the same element-wise test.
3. So if T meets every Aut(P)-orbit on Cores(P): an S8 over P exists iff one exists with core in T.
4. The tree's subtree under a core r holds every S8 with core r: at each hole-stage node the uncovered point p must lie in the
   radical of a form of S8 outside the span, and that form passes the filter and push. This holds at every node for any choice of p,
   and the tree has no memo or pruning across siblings, so the order of points and solids, which g doesn't respect, affects only the
   shape of a subtree, never what it contains.

The symmetry is used at one level only, on an object defined without any ordering (the span, not the path to it). That is why it's
safe where a reduction on path prefixes wouldn't be. Each S8 reaches exactly one core by exactly one path: at each step the form on
the lowest uncovered solid is forced, being the only one in S8. Below a core nothing is reduced, so a dim-4 core's children are all
kept. Using a proper subgroup would still be sound. Only "the generators really stabilise P" and "the action is right" matter for
soundness; that |Aut| is the whole stabiliser matters only for how much is saved.

What the result then says: **no S8 under any listed core, for all 22 P, implies none at all.** It does not enumerate solutions: a
SOLUTION under a representative stands for its orbit, so counts are of the reduced tree.

## Directions from the brief

- **Every solution reaches exactly one core:** yes, statement 4 and the paragraph after it.
- **Right group, right action:** Aut(P) of P as a set, in GL(8,2), acting on the input side. five_orbits' `make_gen` is right: its bit
  conventions agree with `to_coef` and `radical`, and the pointwise evaluation in rv5_indep and the Python in ctl_run agree with it.
  It's a right action, and orbits are unaffected.
- **Ordering:** only the path and tree shape depend on order; see statement 4. Reduced echelon keys are canonical (I checked the
  invariant by hand in both copies); the two copies match, as the kept count proves on all 22.
- **Dim-4 cores:** `is_rep` runs at the push that covers the last solid, whatever the dimension; listed dim-4 cores go through the hole
  stage in phase 1 and their dim-5 children go to the frontier unfiltered. Right. They are 3,665,140 of the 8,154,557 frontier items.
- **Cores below dim 4:** none exist at five. The code would cope: the key pads with zeros, `bydim` and `repdim` have room, phase 1
  descends to dim 5. Three of the four four-solid controls do hold three dim-3 cores each, and five_orbits and the near list handled them, though no
  dim-3 subtree was run. The summary line would understate them (it prints dims 4 and 5 only), but its total stays right.
- **--only, sforms, seeds, tasks:** one config in `cv`, 28 tasks, no seeds in p5.txt, D4 built before parsing. An unknown tag gives
  "covers 0" with a clean done line, but the driver's kept-cores check stops it (tested).
- **Slicing:** the frontier is sorted before the cut and each process rebuilds the same one, so slices partition it. Under `--p1all`
  the `p1only` shortcut is off, in the processes that matter. Phase 2 never calls `is_rep`, since covered is already full.
- **Driver:** no scenario ended in an unflagged clean state where the tally also passed. Killed process, exit 0 with no done line,
  0 or too few cores kept, missing counts line, later frontier mismatch, unknown tag, SOLUTION in phase 1 or 2, FULL, non-APN by count
  alone: each stopped or failed loudly, with no final file where the slice wasn't trustworthy. Real eviction kills the whole Job
  Object tree (read, not exercised); .tmp is never counted.

## Findings, ranked

**Could change the answer: none.**

**Could delay or hide an alarm until the tally (low; worth fixing, none needs a restart)**
1. **"five-a exited 0" does not mean clean; only the tally does.** In run_slice, `os.replace(tmp, final)` comes before `stop(...)`. A
   kill between them leaves a SOLUTION slice final with no STOPPED.txt, and the restart skips it and can finish with exit 0 (tested;
   the window is microseconds, but the job runs for days). The tally does refuse it, and the SOLUTION line stays in the .out. Likewise a
   restart with a different slice size exits 0 and only the tally notices. Fix: call stop before the rename, or at least treat the tally
   as part of the result. This takes effect at the job's next start, and the file can be edited safely while it runs, since Python
   has already loaded it.
2. **`tally` prints an incomplete run instead of failing.** "configurations finished 21 of 22" exits 0. It also doesn't recheck kept
   cores against orbits, which only the driver does, at run time. Before publishing, have it exit non-zero unless 22 of 22, recheck
   `near misses` against the reps files, and grep every .out for the ALARM prefixes.

**Overclaims and stale text (no effect on the search; they matter for the page and for a later reader)**
3. five_orbits' header says "an incomplete list would fail" closure. It wouldn't if the list lacked **a whole orbit**: any union of
   orbits is closed, and "orbit sizes sum to the number of cores" can't fail by construction. So closure alone doesn't show the list
   complete, which is the one thing the reduction most depends on. It **is** complete, by the independent enumeration above, but the
   comment should say so honestly, and the page shouldn't cite closure for completeness.
4. cover.cpp's header still says "every quadratic APN space..." and "No symmetry is used", calls --frange profiling, and the usage
   string omits --reps. The "every" and the "no symmetry" are false for the run that will be published.
5. five_slices.py's docstring says cover5u (EXE is cover5v) and "whole frontier as NEAR lines (~100 MB)"; under --reps it's the listed
   cores, under 1 MB gz on p5-0.
6. README "Five" doesn't mention --reps at all; cfc3795 didn't touch it. notes/work.md's "~8.4M" frontier is **8,154,557** measured.
7. Small: `--reps` without `--only` isn't refused. The driver always passes both, and a missed configuration wouldn't be lost silently
   by that route alone, but the reps file is per configuration and the code could say so.

## Not checked

- **A dim-5 representative with a real solution under it.** Over half the frontier (4,489,417 of 8,154,557 items) and nearly all listed cores are this
  path, and no control can reach it: five has no known solutions, and four-solid cores stop at dim 4. What stands in: `is_rep` is the
  same call at either dimension, the dfs frontier return is six's path unchanged, the 20-representative comparison and the exact
  frontier counts. I think this is adequate, but it is reasoning plus accounting, not a found solution.
- **The hole stage itself**, except as the controls pass through it: review-six.md and review-six-trees.md cover it, and the code is
  unchanged. The shared "B(y,.) outside F_y" test is as it was.
- **The 22 configurations** (pspread, Kurz and Langevin-Hou matches): taken as given. rv5_indep reads the same p5.txt.
- **Rank distribution, Thm IV.5:** taken from the paper; I only redid 75 + 180 = 255.
- **Real eviction and restart:** simulated only. The runner's kill semantics are read, not exercised. Job-level behaviour after exit 3

- rv5_indep shares with cover the mathematical legality test (it has to) and the coefficient order used to read keys. A 64-bit hash

## Suggestions

- Page wording: state the reduction as statements 1 to 4 above, and give 27,987,146 and 4,489,512 as independently recomputed, rather
  than closure as the warrant. Say that A's counts on five are of the reduced tree and aren't comparable with six's or with B's.
- Keep B free of this reduction, or have it derive its own. A symmetry mistake shared by both searches is the one thing a second
  search couldn't catch; B's brief as written already points this way.
- Don't extend the symmetry further for now. Stabilisers of the 95 dim-4 cores could cut their 3.67M children (45% of the frontier), but
  children depend on p, so it needs Stab(r, p) and new code, new review and a restart, to save a part of a job of about five days.
  First slice: 0.053 s of wall per item in a shared room.
